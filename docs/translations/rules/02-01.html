原文译文

8.2　未使用的代码

Rule 2.1　项目中不得含有不可达代码。

[IEC 61508-7 第 C.5.9 节]，[DO-178C 第 6.4.4.3.c 节]

类别
必需（Required）
分析
不可判定（Undecidable），系统（System）
适用标准
C90、C99

理由

只要程序不表现出任何未定义行为，不可达代码就不可能被执行，也不可能对程序输出产生任何影响。因此，不可达代码的存在可能意味着程序逻辑有误。

编译器可以删除任何不可达代码，但没有义务这样做。编译器未删除的不可达代码会浪费资源，例如：

  • 它会占用目标机的存储空间；
  • 当控制流需要绕过不可达代码时，它的存在可能使编译器选择更长、更慢的跳转指令；
  • 如果它在循环内部，就可能使整个循环无法全部放入指令缓存。

为了处理异常情况，有时确实希望插入看似不可达的代码。例如，在一条 switch 语句中，即使控制表达式的每个可能值都有显式的 case 对应，按照 Rule 16.4 仍然必须有 default 子句。该子句用于捕获通常不应出现、但可能因以下原因产生的值：

  • 程序中存在未定义行为；
  • 处理器硬件发生故障。

如果编译器能证明某个 default 子句不可达，它就可能删除该子句，从而消除防护动作。如果这项防护很重要，就必须在以下两种做法中择一：证明编译器尽管知道代码不可达，仍不会将其删除；或者采取措施，使防护代码可达。前一种做法需要办理对本规则的偏离，可能要通过审查目标代码或单元测试来支持偏离。后一种做法通常可通过 volatile 访问实现。例如，对于如下形式的 switch 语句，编译器可能判定 case 子句已覆盖 x 的取值范围：

uint16_t  x;

switch ( x )

如果强制通过一个具有 volatile 限定类型的左值访问 x，编译器就必须假定控制表达式可能取任意值：

switch ( *( volatile uint16_t * ) &x )

注： 被预处理指令有条件排除的代码不受本规则约束，因为它不会进入后续的翻译阶段。

原书示例

enum light { red, amber, red_amber, green };

enum light next_light ( enum light c )
{
  enum light res;

  switch ( c )
  {
    case red:
      res = red_amber;
      break;
    case red_amber:
      res = green;
      break;
    case green:
      res = amber;
      break;
    case amber:
      res = red;
      break;
    default:
    {
      /*
       * This default will only be reachable if the parameter c
       * holds a value that is not a member of enum light.
       */
      error_handler ( );
      break;
    }
  }

  return res;
  res = c;                      /* Non-compliant - this statement is
                                 * certainly unreachable               */
}

原书代码注释中译： 仅当形参 c 保存的值不是 enum light 的任何一个成员值时，这个 default 分支才可达。return 后的 res = c; 不合规——这条语句一定不可达。
