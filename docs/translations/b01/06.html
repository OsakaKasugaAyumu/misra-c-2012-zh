原文译文

本节介绍第 7 节和第 8 节中准则的呈现方式。这两节是本文件的主体，本节为其导读。

6.1 准则的种类

每项 MISRA C 准则要么是一条“规则”（rule），要么是一条“指令”（directive）。

指令是一种无法仅用其自身的描述就给出合规检查所需全部信息的准则。要实施检查，还需要设计文档或需求规格说明等材料提供的额外信息。静态分析工具可能有助于检查指令的合规性，但对于什么构成不合规，不同工具的解释可能大相径庭。

规则是一种已经完整描述了要求的准则。应当可以不借助任何其他信息，检查源代码是否符合一条规则。具体来说，在 §6.5 所述限制下，静态分析工具应当能够检查规则的合规性。

所有指令都在第 7 节，所有规则都在第 8 节。

6.2 准则的类别

每条 MISRA C 准则都归入且只归入“强制”（mandatory）、“必需”（required）或“建议”（advisory）三类之一，含义如下。除这一基本分类外，本文件不对各项准则的重要性作进一步分级，也无意暗示这种分级。所有必需类准则，无论是规则还是指令，均应视为同等重要；强制类内部、建议类内部也分别如此。

6.2.1 强制类准则

声称符合本文件的 C 代码必须遵守每一条强制类准则；不允许偏离强制类准则。

注： 由于 §6.5 中说明的原因，检查工具给出一条诊断消息，并不一定意味着违反了准则。

6.2.2 必需类准则

声称符合本文件的 C 代码必须遵守每一条必需类准则；未遵守时，必须按 §5.4 所述办理正式偏离。

组织或项目可以选择将任何一条必需类准则按强制类准则对待。

6.2.3 建议类准则

这些是建议。不过，“建议”并不意味着可以置之不理，而是应在合理可行的范围内尽量遵守。建议类准则不要求办理正式偏离；如果不采用正式偏离流程，则应另行安排，将不合规之处记入文档。

组织或项目可以选择将任何一条建议类准则按强制类或必需类准则对待。

6.3 准则的编排

准则按 C 语言的不同主题编排。不过，各个主题难免重叠，一条准则可能涉及多个主题。遇到这种情况时，将该准则列在最相关的主题下。

6.4 准则中的冗余

有少数准则涉及的语言特性，在本文件其他地方已被禁止或不建议使用。这是有意安排的。使用者仍可能选择使用该特性：对必需类准则申请偏离，或选择不遵守建议类准则。这时，另一条约束该特性用法的准则就有了用处。

6.5 规则的可判定性

每条强制类、必需类和建议类规则，都被标为可判定或不可判定。这种分类描述的是静态分析器回答“这段代码是否符合这条规则”这一问题的理论能力。指令没有这种划分，因为仅凭源代码，不可能设计出能够保证完成合规检查的算法。

如果可以编写一个程序，对每一种情况都能给出“是”或“否”的答案，该规则就是可判定的，否则就是不可判定的。这一划分以计算理论为基础，回顾该理论超出了本文件范围。不过，若检出违规依赖下列运行时性质，规则很可能不可判定：

  • 某个对象所保存的值；
  • 控制流是否到达程序中的某一位置。

对于静态分析，可判定规则具有一些有用的性质。前提是静态分析器没有缺陷、功能完备，且配置正确：

  • 若报告违反一条可判定规则，就说明确实存在违规；
  • 若未报告违反一条可判定规则，就说明被分析的代码中没有违反该规则之处。

可判定规则的例子包括：

  • Rule 5.2：取决于标识符的名称和作用域；
  • Rule 11.3：取决于源指针类型和目标指针类型；
  • Rule 20.7：取决于宏展开结果的语法形式。

对于不可判定规则，不同静态分析器检出违规的能力各不相同：

  • 报告违反一条不可判定规则，不一定说明确实违规；有些分析器会将其报告为可能违规，以提醒使用者结论并不确定；
  • 未报告违反一条不可判定规则，也不一定说明被分析的代码中没有违规之处。

不可判定规则的例子包括：

  • Rule 12.2：取决于移位运算符右操作数的值；
  • Rule 2.1：取决于能否知道程序执行永远不会到达某一位置。

如 §5.3.3 所述，应制定分析静态分析结果并记录结论的流程。对于涉及不可判定规则的任何输出，应特别留意其分析流程。

6.6 分析范围

每条规则还按检出违规所需检查的代码范围分类。与可判定性一样，分析范围的概念也不适用于指令。

规则的分析范围可以是“单一翻译单元”（Single Translation Unit）或“系统”（System）。

如果一条规则能够在单一翻译单元的范围内检查，那么分别独立检查每个翻译单元，就可以检出整个项目中对该规则的所有违反。例如，一个翻译单元中存在不含 default 标签的 switch 语句（Rule 16.4），并不影响其他翻译单元中是否有这类 switch 语句。

如果一条规则需要在系统范围内检查，那么要识别某个翻译单元中的违规，就不能只检查该翻译单元。检查“系统”类规则最好分析全部源代码，尽管只检查一部分源码也能识别某些违规。例如，假设项目有 A、B 两个翻译单元，可以分别在每个翻译单元内，检查某个对象的所有声明和定义是否使用相同的类型名和限定符（Rule 8.3）。但这样不能保证 A 中的声明和定义使用的类型名和限定符与 B 中的一致。因此，要保证符合该规则，必须检查将被编译并链接进可执行文件的所有源代码。

所有不可判定规则都需要在系统范围内检查，因为一般而言，还需要知道其他翻译单元的行为。例如，在下列函数 g 中，自动存储期对象 x 的值在使用前是否已被设置（Rule 9.1），取决于另一个翻译单元中定义的函数 f 的行为：

extern void f ( uint16_t *p );

uint16_t  y;

void g ( void )
{
  uint16_t  x;  /* x is not given a value                                */

  f ( &x );     /* f might modify the object pointed to by its parameter */
  y = x;        /* x may or may not be unset                             */
}

原书注释中译： 声明时未给 x 赋值；f 可能修改其参数所指向的对象；读出 x 时，它可能尚未被赋值，也可能已经被赋值。

6.7 多组织协作项目

项目可能使用来自不同组织的代码，例如：

  • 编译器实现者提供的标准库代码；
  • 器件供应商提供的底层驱动程序代码；
  • 专业供应商提供的操作系统和高层驱动程序代码；
  • 应用程序代码，协作组织可以按各自专长分担开发。

标准库代码通常重视执行效率，可能依赖实现细节或未指定行为，例如：

  • 将指向一种对象类型的指针强制转换为指向另一种对象类型的指针；
  • 依赖栈帧的布局，特别是函数参数在栈帧中的位置；
  • 在 C 中嵌入汇编语言语句。

标准库是实现的一部分，其功能和接口由 ISO C 标准定义，因此不要求标准库代码符合 MISRA C。除非个别准则另有规定，标准头文件的内容以及处理标准头文件时所包含的任何文件，都不要求符合 MISRA C。但是，涉及标准头文件中的声明和宏所提供接口的准则仍然适用。例如，本质类型规则仍适用于传给标准库所规定函数的实参类型，以及这些函数的结果类型。

所有其他代码都应尽可能符合 MISRA C 准则。如果可以取得全部源代码，就可以检查整个程序的合规性。但在许多项目中，开发组织无法取得全部源代码。例如，协作组织可能共享功能规格、接口规格和目标代码，却很可能不共享源代码，以保护各自的知识产权。在只有部分源代码可供分析时，应使用其他技术来确认合规性。例如：

  • 提供商业代码的组织可能愿意出具 MISRA C 合规声明；
  • 相互协作的组织可以：
    • 商定共同的程序和工具，由各方分别用于自己的源代码；
    • 相互提供源代码的桩版本，以便实施跨组织检查。

项目应明确采用下列哪一种方式处理其他组织提供的代码：

  1. 按与内部开发代码相同的方式处理——前提是能够取得源代码；
  2. 按与标准库相同的方式处理——前提是提供方出具适当的 MISRA C 合规声明；
  3. 检查头文件内容及其接口的合规性——这里假设没有可用的合规声明，除头文件外也没有可用的源代码。

对于第（3）种情况，在使用代码之前，应采用适当的附加验证和确认技术。

注： 一些过程标准可能对多组织协作开发的管理提出更广泛的要求，例如 ISO 26262 [23] 第 8 部分第 5 条“分布式开发中的接口”。

6.8 自动生成的代码

MISRA C 准则同样适用于自动生成的代码。自动代码生成工具的开发者和用来生成代码的模型的开发者，都对合规性负有责任。由于建模软件包不止一种，而每种软件包又可能有多个自动代码生成器，不可能针对每一条 MISRA C 准则分别指定由哪一方负责。预期建模软件包和代码生成器的使用者会采用相关指南，如 MISRA AC GMG [17]、MISRA AC SLSF [18] 和 MISRA AC TL [19]。

同一条 MISRA C 准则适用于自动生成代码时的类别，不一定与其适用于手写代码时相同。在区分二者时，务必注意某些建模软件包允许向模型中插入手写代码。在确定某条准则的适用类别时，这类代码不按自动生成代码处理。

附录 E列出了对自动生成代码与手写代码分配不同类别的 MISRA C 准则，也说明了对自动代码生成器开发者的文档要求。

此外，每一项或每一组相关条目都配有说明文字。在适当情况下，说明文字会解释准则所针对的根本问题，并给出如何应用准则的示例。

说明文字中可能有一个标题为“进一步说明”（Amplification）的部分，其后的文字对准则作更精确的描述。进一步说明具有规范效力；如果它与准则的标题句相冲突，以进一步说明为准。这样就可以用简短的标题句表达复杂的概念。

说明文字中还可能有一个标题为“例外”（Exception）的部分，其后的文字描述该规则不适用的情况。使用例外可以简化某些准则的描述。重要的是，例外指该准则不适用的情形。由于符合例外条件而符合准则的代码，无须办理偏离。

说明文字不是相关语言特性的教程，这里假定读者已具备运用该语言的知识。如需进一步了解这些特性，可查阅语言标准的相关章节或其他 C 语言参考书。如果准则引用了 C 标准列出的一项或多项“可移植性问题”，查阅标准中提出的原始问题，也有助于理解准则。

准则及其说明文字使用下列字体样式来表示 C 关键字和 C 代码：

  • C 关键字以斜体显示；
  • 术语表中定义的词以斜体显示；
  • C 代码用等宽字体显示，可以嵌在其他文字之中；
  • 也可以
    另列为独立的代码片段。

注： 为简明起见，所引的代码片段可能不完整（例如，只有 if 语句而没有其语句体）。

下列代码片段假定已用 typedef 定义了以下类型（这是为了符合 Dir 4.6）：

uint8_t           /* unsigned 8-bit integer  */
uint16_t          /* unsigned 16-bit integer */
uint32_t          /* unsigned 32-bit integer */

原书注释中译（依次对应八行）： 无符号 8 位、16 位、32 位整数；有符号 8 位、16 位、32 位整数；32 位、64 位浮点数。

无特定含义的对象名构造成能提示其类型的形式。例如：

uint8_t   u8a;    /* 8-bit unsigned integer  */

bool_t    bla;    /* essentially Boolean     */

原书注释中译（依次对应八行）： 8 位无符号整数；16 位有符号整数；32 位有符号整数；本质布尔类型；枚举类型；字符；32 位浮点数；64 位浮点数。

6.10 如何理解来源引用

当一条准则源自一个或多个已出版的来源时，会在准则之后用方括号标明。这有两个目的。第一，希望更充分理解准则制定理由的读者（例如在考虑一项偏离申请时），可以查阅具体来源。第二，对于 ISO C 标准中描述的可移植性问题，引用形式还提供了有关问题性质的额外信息。

没有来源引用的规则，可能源于参与编制的某家公司的内部标准，可能是审查者的建议，也可能是受到广泛认可的良好实践。

6.10.1 ISO C 可移植性问题的引用

ISO C 的可移植性问题列在相应标准附录的各个小节中。务必注意，对 C90 和 C99 而言，引文编号都取自最初的标准，而不取自纳入了勘误和修订的后续版本。这样决定一部分是出于历史原因：MISRA C:2004 就采用了这个编号办法；另一部分是出于实际考虑：虽然有草案 [12]，但并无纳入各项技术勘误的正式 C99 标准修订本可供获取。

这类引用与相应标准小节的对应关系如下：

引用标记ISO 9899:1990 附录 GISO 9899:1999 附录 J
Unspecified（未指定）G.1J.1
Undefined（未定义）G.2J.2
Implementation（实现定义）G.3J.3
Locale（地域相关）G.4J.4

引用标记后所附文字的含义如下：

  • 引用 [2] 附录 G 时，文字指明该附录相应小节中一个或多个条目的编号，编号从该小节的开头算起。例如，[Locale 2] 指该标准 §G.4 的第 2 项，[Undefined 3, 5] 指 §G.2 的第 3 和第 5 项。
  • 引用 [8] 附录 J 时，对于 §J.1、§J.2 和 §J.4，沿用上述解释。对于 §J.3，文字先指明 J.3 下的小节，再在括号中给出一个或多个条目编号。例如，[Unspecified 6] 指该标准 §J.1 的第 6 项，[Implementation J3.4(2, 5)] 指 §J.3.4 的第 2 和第 5 项。

当准则是根据 C 标准附录 G（C90）或附录 J（C99）中的问题制定时，区分 Unspecified、Undefined、Implementation 和 Locale 四种引用，对读者很有帮助。下面给出简要解释；更多信息可参阅 Hatton [3]。

未指定（Unspecified）

这类语言构造必须能成功编译，但编译器编写者对构造的具体效果有一定选择自由。Rule 13.2 中所述的“求值顺序”就是一例。

有些未指定行为难以避免，但假定编译器生成的目标代码一定会按某种特定方式运行，并不明智；编译器甚至不必对所有可能的构造采取一致做法。

MISRA C 指出了未指定行为中容易产生不安全行为的具体情形。

未定义（Undefined）

这些本质上是编程错误，但编译器编写者没有义务给出错误消息。例如，传给函数的参数无效，或者调用函数使用的实参与其定义的形参不匹配。

从安全角度看，这些情形尤其重要，因为它们属于编译器未必能发现的编程错误。

实现定义（Implementation）

这些问题与“未指定”问题相似，主要区别在于编译器编写者必须采用一致的做法并形成文档。也就是说，具体功能可以因编译器而异，使代码不具可移植性；但在任何一个给定编译器上，行为应当是明确定义的。一个例子是整数除法和取余运算符 / 和 % 作用于一正一负两个整数时的行为。

从安全角度看，实现定义行为往往没有那么关键，前提是编译器编写者已完整记录预期做法，并在实现时保持一致。尽可能避开这些问题是明智的。

地域相关（Locale）

与地域相关的行为构成一小组可能随不同国家和地区要求而变化的特性。例如，可以用逗号（,）代替句点（.）来表示小数点。本文件不涉及源自这一类的问题。
