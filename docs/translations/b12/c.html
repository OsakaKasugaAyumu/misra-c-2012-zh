附录 C　C 的类型安全问题

底本定位 PDF 201–203 ／ 印刷 193–195 · 源页说明

本页目录
  • C.1 类型转换
  • C.2 开发者可能产生的误解

原文译文

由于 ISO C 允许多种隐式类型转换，可以认为它的类型安全性较弱。这些转换有些方面由实现定义，容易使开发者误解，从而危及安全。

下面说明这些转换，并举例展示它们如何使开发者产生误解。

C.1 类型转换

C.1.1 隐式转换

ISO C 的隐式类型转换使表达式可以混合使用不同类型；即使所用类型完全相同，也可能发生转换。隐式转换分为三种：

  1. 按照 C90 §6.2.1.1、C99 §6.3.1.1，只要将位域，或类型为有符号／无符号 char、有符号／无符号 short 或 enum 的对象用于算术运算，就会发生整数提升，转换为 signed int 或 unsigned int。整数提升保留原值，但符号性可能改变（例如 unsigned char 会转换为 signed int）。
  2. 如 C90 §6.2.1.5、C99 §6.3.1.8 所述，当某些运算符的操作数类型不同时，通常算术转换将操作数转换（平衡）到一个共同类型。
  3. 赋值时的转换。

如下例所示，一个表达式可能不发生上述任何转换，也可能发生一种、两种或全部三种转换（si 和 ui 分别是 32 位有符号和无符号整数，u8 是 8 位的 unsigned char）：

表达式提升平衡转换说明
si = si + si;
si = uc + uc;是uc 提升为 signed int
ui = si + ui;是si 平衡到 unsigned int
ui = ui + uc;是是uc 提升为 signed int，再平衡到 unsigned int
ui = si;是si 转换为 unsigned int
ui = uc + uc;是是uc 提升为 signed int，表达式的结果转换为 unsigned int
si = si + ui;是是si 平衡到 unsigned int，表达式的结果转换为 signed int
si = ui + uc;是是是uc 提升为 signed int，再平衡到 unsigned int，表达式的结果转换为 signed int

C.1.2 显式转换

可以出于以下功能上的原因引入显式类型转换（强制转换）：

  • 改变后续算术运算所使用的类型；
  • 有意截断一个值；
  • 明确写出类型转换，使含义更清楚。

ISO C 并不要求检查所有显式强制转换，因此不兼容类型之间也能进行转换。

C.1.3 转换带来的问题

隐式转换和显式转换都可能带来若干问题，包括：

  • 数值损失：例如，转换到不能表示该值大小的类型。
  • 符号丢失：例如，从有符号类型转换到无符号类型，导致符号丢失。
  • 精度损失：例如，从浮点类型转换到整数类型，因而损失精度。
  • 存储布局不再匹配：例如，把指向一种类型的指针转换为指向另一种类型的指针，导致存储布局不兼容。

许多类型转换都是安全的，但对所有数据值以及所有可能的符合标准的实现都能保证安全的转换只有：

  • 把整数值转换到符号性相同、宽度更大的整数类型；
  • 把浮点类型转换到宽度更大的浮点类型。

取决于实现采用的整数宽度，其他类型转换也可能是安全的。不过，凡是有潜在危险的类型转换，都应显式写出，以便识别。

C.2 开发者可能产生的误解

不同实现中类型的大小可能不同，因此发生隐式转换的场合也可能不同。这要求开发者对每个具体项目使用的类型系统都要心中有数。开发者很容易偶尔用错模型，尤其是在同时参与采用不同实现的多个项目时。

C.2.1 整数提升中的类型拓宽

整数表达式以何种类型求值，取决于操作数经过整数提升后的类型。两个 8 位值相乘，结果的宽度总是至少为 16 位；但两个 16 位值相乘，只有在实现的 int 至少为 32 位时才会得到 32 位结果。较安全的做法是始终不依赖整数提升带来的类型拓宽，因为相关的实现定义行为可能使开发者产生误解。考虑以下示例：

uint16_t u16a = 40000; /* unsigned short or unsigned int ? */
uint16_t u16b = 30000; /* unsigned short or unsigned int ? */
uint32_t u32x;         /* unsigned int or unsigned long ? */
u32x = u16a + u16b;    /* u32x = 70000 or 4464 ?  */

原注：前两个对象的类型是 unsigned short 还是 unsigned int？第三个是 unsigned int 还是 unsigned long？结果是 70000 还是 4464？

预期的结果可能是 70 000，但赋给 u32x 的值取决于实现的 int 大小。若为 32 位，加法使用 32 位有符号算术，得到“正确”的值。若仅为 16 位，加法使用 16 位无符号算术，发生回绕，得到 4 464（70 000 % 65 536）。无符号算术中的回绕有明确定义，但其效果取决于运算所用的类型，因此有意利用回绕时应形成文档。

C.2.2 对求值类型的误解

类似的问题是，开发者误以为计算所用的类型会受接收结果的类型或结果要转换到的类型影响。例如，在下面的代码中，两个 16 位对象以 16 位算术相加（假设 int 为 16 位），到赋值时才将结果转换为 uint32_t。

u32x = u16a + u16b;

由于 u32x 的类型而误以为加法使用 32 位算术，这种情况并不少见。

这类误解不限于整数算术，也不限于隐式转换。以下语句的结果都有明确定义，但计算未必以开发者预期的类型进行：

u32a = (uint32_t)(u16a * u16b); /* May not be a 32-bit operation */
f64a = u16a / u16b;       /* Not floating point division */
f32a = (float32_t)(u16a / u16b); /* Not floating point division */
f64a = f32a + f32b;       /* May be a low precision operation */
f64a = (float64_t)(f32a + f32b); /* May be a low precision operation */

原注（依语句顺序）：第一行未必是 32 位运算；第二、三行都不是浮点除法；第四、五行都可能是低精度运算。

C.2.3 算术运算中符号性的改变

整数提升可能使表达式的结果不符合开发者的预期。例如，表达式 10 - u16a 的结果取决于 int 的大小。若 u16a 为 100 且 int 为 32 位，则结果有符号，值为 −90。但若 int 为 16 位，结果将是无符号的 65 446。

C.2.4 按位运算中符号性的改变

对较小的无符号类型使用按位运算符时，整数提升可能造成误解。例如，对 unsigned char 类型的操作数按位取反，通常会得到类型为（有符号）int 的负值。运算前，操作数被提升到 int，取反会将新增的高位置一。是否有新增位以及有多少位，取决于 int 的大小；取反之后再右移尤其危险，因为这会导致实现定义行为。

u8a = 0xff;
if ( ~u8a == 0x00U ) /* This test will always fail */

原注：这项测试总会失败。
