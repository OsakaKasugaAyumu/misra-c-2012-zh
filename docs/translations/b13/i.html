I.1　概述

MISRA C:2012 Rule 10.6 的理由是避免开发者误解某些算术运算实际采用的类型。不幸的是，由于本项目使用的编译器有一项“特性”，要使代码符合这条规则，就不可避免地会严重降低运行时性能。这样，软件便无法在所有情况下都满足时序要求，车辆达不到法定碳氢化合物排放目标的风险也相当大。

I.2　详细说明

项目使用了若干变时间步长积分器，用多精度数长期累加求和。待积分的量和积分时间步长都是 16 位无符号量；需要先将两者相乘得到 32 位结果，再进行累加。

由于本项目所用的 C 编译器把 int 实现为 32 位，计算 32 位乘积的代码如下：

extern uint16_t qty, time_step;

uint32_t  prod = ( uint32_t ) qty * ( uint32_t ) time_step;

显然，尽管乘法运算符的两个操作数均为 32 位，乘积也不可能大到 32 位容纳不下，因为两个操作数都是从 16 位经零扩展得到的。

按照我们的标准开发程序，所有目标模块都要交给最坏情况执行时间分析工具，以确保每个函数符合架构设计中为它规定的执行时间预算。分析工具指出，为这些积分器生成的代码远远超出了分配给它们的时间预算。调查发现，执行时间过长，是因为编译器生成了对采用“移位加法”的长乘法例程的调用。这一点令人意外：处理器配有一条 IMUL 指令，能在一个时钟周期内把两个 16 位无符号整数相乘，得到 32 位结果。尽管乘法的两个操作数是 32 位的，编译器有办法知道它们的高 16 位全是 0，因此应该能选择 IMUL 指令。

用该编译器所做的实验表明，只要让乘法操作数从 16 位隐式转换到 32 位，它就会选择 IMUL 指令，即：

uint32_t  prod = qty * time_step;

这尤其奇怪，因为按照 C 标准的描述，这段代码的行为并不取决于转换是隐式还是显式。无论乘法使用 IMUL 还是库调用，程序都会得到相同的结果，但库调用在最坏情况下需要 100 个周期才能执行完毕。编译器供应商已书面确认，这正是他们在该情况下所预期的行为。

I.3　理由

项目中有多个函数使用这种积分器，平均每 100 微秒至少执行一次，因此库函数的性能不能接受。在规定的 25 MHz CPU 内部时钟频率下，这意味着仅这些乘法就要占去 4% 的时间。这一点本身并不严重，总体时序预算中有余量可以容纳。然而，设计规定积分器必须在最多 10 微秒内给出结果，才能满足其他函数的时序要求。达不到这一要求，就会给实现排放目标带来重大风险，其商业影响超过 1,000 万美元。

我们首选的解决办法是使用隐式转换来编写积分器。这要求为此类积分器的实例申请偏离 MISRA C:2012 Rule 10.6。这样生成的代码与使用符合 MISRA 的写法所生成的代码在功能上相同，但执行速度最高可达后者的 100 倍。

还考虑了以下其他方案：

  • 提高时钟频率——要达到所需性能，时钟频率必须提高到原来的 10 倍；但该处理器的 PLL 最高频率为 100 MHz。
  • 更换处理器——硬件设计确认工作已深入进行，从商业角度看不可行；项目的额外成本约为 25 万美元，进度也会受到影响。
  • 更换编译器——没有其他得到商业认可的编译器可用于这款处理器。虽有一款无人提供支持的公有领域编译器，但认为其质量不适合本项目。
  • 重写库例程——该库使用以 2 为基数的长乘法。可以改写为用 3 条 IMUL 指令实现以 65 536 为基数的长乘法，但我们不愿改动编译器供应商的代码。我们就这个方案征求了供应商意见，得到的答复是：“他们无法为我们修改其库的做法提供支持。”

I.4　申请偏离所适用的条件

本次偏离申请适用于项目中所有变时间步长积分器的实例。

I.5　不合规的后果

在本偏离记录所述情形下，不符合 MISRA C:2012 Rule 10.6 不产生后果。

本次偏离不会带来额外的验证和确认要求。

I.6　控制诊断报告的措施

用于检查该规则合规性的 MMMC 工具提供了在表达式内抑制诊断消息的功能。由于所有积分器均具有以下形式：

prod = qty * time_step;

可以用宏实现积分器并抑制警告。将使用下面的宏来进行乘法，并把结果赋给乘积项：

/* Violates Rule 10.6: See deviation R_00102 */
#define INTEG(prod, qty, time_step) \
   ( /* -mmmc-R10_6 */ (prod) = (qty) * (time_step) /* -mmmc-pop */ )

原书代码注释中译：违反 Rule 10.6；见偏离记录 R_00102。

虽然可以把这个宏实现为函数，但考虑到所执行的运算很简单，调用和返回的开销太大。因此，即使这意味着违反 Dir 4.9，这里仍优先选择宏而不是函数。
